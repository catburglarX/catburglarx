## The problem

In India, Legal Metrology officers check packets in shops. They look for things the law says must be printed, like the price, the weight and who made it. Most of this still goes on a paper form.

Paper has a big gap. Months later, if a shop owner says the check was wrong, the packet is gone. There may be no photo. Nobody wrote down how the numbers were worked out.

A blank box on the form is the hardest part. It can mean three different things:

- The packet really doesn't show the detail. That breaks the rule.
- The photo only shows the front, so nobody saw the back.
- The detail is there, but it's too blurry to read.

Only the first one is a real problem. On paper, all three look the same.

## What I built

With Maanak, the officer takes a photo instead of filling in a form. The app:

1. Checks if the photo is clear enough, and says what to fix, like "strong glare is covering part of the panel".
2. Reads the label in English and Hindi.
3. Shows every value next to the part of the photo it came from.
4. Lets the officer confirm, correct or reject each value.
5. Runs the rules only on values the officer confirmed.
6. Makes a report that is locked, so nobody can change it later.

Here is the idea in numbers. On one test inspection, before the officer checked anything, the app gave 7 "need more evidence", 3 "can't tell" and 0 violations. After the officer checked the same photo, 10 rules could run and 1 violation showed up. The photo didn't change. The officer's check did.

## Stack

FastAPI runs the API. A separate worker reads the labels, so nobody waits on it. PostgreSQL stores the data, Redis holds the queue, MinIO stores the photos, and nginx serves the pages. The front end is plain HTML, CSS and JavaScript with no build step. It all starts with one command:

```bash
cp .env.example .env
docker compose up --build -d
```

Money is never stored as a float. It uses `Decimal`, so the paisa is always right:

```python

# 119.15, not the 119.14 a phone calculator gives
```

## The hardest problem

Reading real labels. On labels the project makes itself, the reader gets 72 of 80 values right. All 8 misses are the same mistake. It reads "Iodised" as "lodised", because a capital I and a small l look the same in most fonts. I didn't add a rule to "fix" it, because that rule would also turn "Lemon" into "Iemon". The app tells the officer instead.

Real photos were much harder. I tested 14 photos of Indian packets from Open Food Facts. Only 6 gave any value at all, and none gave the weight. So I built the app to expect this. Across all 14 photos, it raised 0 violations before an officer checked them.

## What I learned

- When the app can't read something, a person should look at it. It should never become a violation on its own.
- Test with the strict question. One early test counted a hit if the number or the unit showed up anywhere. It made a useless change look like a big win.
- Be honest about what's missing. The project lists what isn't done yet, like HTTPS and an outside security review.
- Put important rules where they can't be skipped. The "only use checked values" rule lives inside the rule engine, not just on the screen.
